# YU-RIS adaptation lessons, 2026-11-26 (Monochrome Empire, cold test / adapt-auto)

- The title menu takes no PostMessage click and no hover + click; injected InputShim (fake foreground, GetCursorPos, GetAsyncKeyState, DirectInput) is enough: the start item opened on the first shim click. The cold test's input ladder (core/cold-test/input-fallback.cjs) escalates PostMessage → InputShim → SendInput (visible runs only) by itself and records the level in run.json `input`
- Once input lands, blind advance clicks are dangerous on a menu: the bottom-centre click opened 「各鑑賞モード」 before the OCR had found 「最初から始める」. adapt-auto holds blind clicks on a few-line screen until the OCR has looked once (driver `holdBlind`)
- Name entry is a standard Win32 dialog (#32770 「名前入力」, Edit + OK), three in a row (surname, given name, katakana reading). The script line before it offers the default (「アナタの名字を入力してください」 + 朽木); an empty Edit filled with that name and OK pressed by BM_CLICK passes all three (the game took the kanji for the reading too)
- A 150-character system text arrives before the title and counts as line 1, so the run is in the advance phase on the title; stale OCR menu items must be dropped once a line came or a click took, or the title's start item is clicked again on the next screen and looks like ignored input
- After the name entry the dialogue reaches the hook with every character repeated eight times (「誕誕誕誕誕誕誕誕生生生生…」, YU-RIS / YU-RIS2 threads). Before the reader-nodraw merge HookBridge dropped them as aux noise (5 lines); after it they are kept as script noise lines (79 "lines"), still 8x repeated, and Cardinal finds no dialogue in them. The repeat collapse belongs in HookBridge (native/), not done here

# YU-RIS engine layer, 2026-11-26 (branch engine-yuris, HookBridge only)
- Why 8x: the game draws every glyph eight times with TextOutA (outline). YU-RIS2 is the hook on that TextOutA call and YU-RIS the other glyph hook, so both read 「誕誕誕誕誕誕誕誕生生生生生生生生」, two characters per flush while typing and the rest at once on a click; yuris7 carries the same pieces once; yuris9 (selected first) only carries script resource names ("ysr003")
- Bridge (only for stream names YU-RIS*/yuris*/EmbedYURIS*): a stream learns its repeat factor from a text made only of runs of a common length (N >= 3 over two runs, or N = 2 over four) and folds every later text by it (a run shorter than N stays, a cut-off run over N/2 counts as one); pieces are joined into lines with the KiriKiri joiner (sentence end, new opening mark, 1.2 s quiet); a complete line on a higher ranked stream (YU-RIS2 > YU-RIS > yuris7) takes the selection unless a writable stream (EmbedYURIS6) is selected; the rival switch no longer pulls between folded YU-RIS siblings. A YU-RIS game that never repeats glyphs is unchanged
- Name plates come as 「朽木木朽木木…」 (each of the N passes reads the name from every glyph on): found and sent as hookName from the selected stream. Live r4 still shows some chains mid-line (「主神神主神神…」) when the chain is split across flushes (not fixed)
- Hiding: joined lines reach the glyph layer after the typewriter drew them (placed=0), so that layer never hides here. YU-RIS2 is the TextOutA call itself, so the DLL's GDI hide (MeguLitGdiHide.h) blanks each glyph it was just fed: the bridge now switches a selected folded YU-RIS2 stream on for it (DotsOwn otherwise keeps gdiProbe streams off). This is source no-draw already (the draw call draws nothing), so no MeguLitDrawSkip registration and no native rebuild were needed. Risk: choices drawn through the same TextOutA call are hidden too (not seen live: no choice within the run)
