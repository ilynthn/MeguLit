# YU-RIS adaptation lessons, 2026-11-26 (Monochrome Empire, cold test / adapt-auto)

- The title menu takes no PostMessage click and no hover + click; injected InputShim (fake foreground, GetCursorPos, GetAsyncKeyState, DirectInput) is enough: the start item opened on the first shim click. The cold test's input ladder (core/cold-test/input-fallback.cjs) escalates PostMessage → InputShim → SendInput (visible runs only) by itself and records the level in run.json `input`
- Once input lands, blind advance clicks are dangerous on a menu: the bottom-centre click opened 「各鑑賞モード」 before the OCR had found 「最初から始める」. adapt-auto holds blind clicks on a few-line screen until the OCR has looked once (driver `holdBlind`)
- Name entry is a standard Win32 dialog (#32770 「名前入力」, Edit + OK), three in a row (surname, given name, katakana reading). The script line before it offers the default (「アナタの名字を入力してください」 + 朽木); an empty Edit filled with that name and OK pressed by BM_CLICK passes all three (the game took the kanji for the reading too)
- A 150-character system text arrives before the title and counts as line 1, so the run is in the advance phase on the title; stale OCR menu items must be dropped once a line came or a click took, or the title's start item is clicked again on the next screen and looks like ignored input
- After the name entry the dialogue reaches the hook with every character repeated eight times (「誕誕誕誕誕誕誕誕生生生生…」, YU-RIS / YU-RIS2 threads). Before the reader-nodraw merge HookBridge dropped them as aux noise (5 lines); after it they are kept as script noise lines (79 "lines"), still 8x repeated, and Cardinal finds no dialogue in them. The repeat collapse belongs in HookBridge (native/), not done here

# YU-RIS engine layer, 2026-11-26 (branch engine-yuris, HookBridge only)
- Why 8x: the game draws every glyph eight times with TextOutA (outline). YU-RIS2 is the hook on that TextOutA call and YU-RIS the other glyph hook, so both read 「誕誕誕誕誕誕誕誕生生生生生生生生」, two characters per flush while typing and the rest at once on a click; yuris7 carries the same pieces once; yuris9 (selected first) only carries script resource names ("ysr003")
- Bridge (only for stream names YU-RIS*/yuris*/EmbedYURIS*): a stream learns its repeat factor from a text made only of runs of a common length (N >= 3 over two runs, or N = 2 over four) and folds every later text by it (a run shorter than N stays, a cut-off run over N/2 counts as one); pieces are joined into lines with the KiriKiri joiner (sentence end, new opening mark, 1.2 s quiet); a complete line on a higher ranked stream (YU-RIS2 > YU-RIS > yuris7) takes the selection unless a writable stream (EmbedYURIS6) is selected; the rival switch no longer pulls between folded YU-RIS siblings. A YU-RIS game that never repeats glyphs is unchanged
- Name plates come as 「朽木木朽木木…」 (each of the N passes reads the name from every glyph on): found and sent as hookName from the selected stream. Live r4 still shows some chains mid-line (「主神神主神神…」) when the chain is split across flushes (not fixed)
- Hiding: joined lines reach the glyph layer after the typewriter drew them (placed=0), so that layer never hides here. YU-RIS2 is the TextOutA call itself, so the DLL's GDI hide (MeguLitGdiHide.h) blanks each glyph it was just fed: the bridge now switches a selected folded YU-RIS2 stream on for it (DotsOwn otherwise keeps gdiProbe streams off). This is source no-draw already (the draw call draws nothing), so no MeguLitDrawSkip registration and no native rebuild were needed. Risk: choices drawn through the same TextOutA call are hidden too (not seen live: no choice within the run)
- Live: r1 (fold+join+select) fail 377 s, 93 lines, Cardinal row 0.75 clean 0.75 pair 1 leak 0 (read mode, hide never confirmed). r4 (+GDI hide, name, rounding) inconclusive 468 s, cold pass 100 lines, `gdi hide confirmed for YU-RIS2 (fn=TextOutA size=92)`, Cardinal leak 1 but scored 0 lines although the tape holds 60 dialogue lines (warmup until 4344 ms; cause not found, Cardinal layer, not changed). r2/r3: the game window stayed white before the notice screen (environment, r4 with the same code passed)

# YU-RIS auto adaptation follow-up, 2026-11-27 (branch feat/auto-adapt)
- Why "Cardinal scored 0 lines" on r4: the cold run's tape kept the in-memory default of 60 lines, all of them after Ctrl went down, and Cardinal does not score the Ctrl span. The worker now keeps up to 400 lines and writes the Ctrl span plus the 60 reading-pace lines before it (a Ctrl span over 60 lines keeps its first and last 30); adapt-auto replays the whole tape (--lines)
- Why every hidden run stalled after 2 lines: the name entry is a #32770 dialog, answered by services/cold-input.ps1 with EnumThreadWindows from the visible desktop, which does not see the hidden desktop. r1/r4 passed only because they ran with --foreground. ColdDesk (on the game's desktop) now answers "dialog <name>" itself on hidden runs; the name is URI-encoded (ColdDesk reads stdin in the ANSI code page: the first live run typed 「麻?」)
- Name plates split across flushes (「…」主神神主神神…「…」 in one line) are looked for again in the joined line (two passes enough there); a 。 inside an open quote no longer ends the joined line
- Reading pace: YU-RIS hands the joined line over when its typewriter is done; the click came 1.2 s later and the reader (revealing again at about 30 characters a second) never finished 10 of 55 lines (row 0.818). adapt-auto now waits 45 ms a character for engines in WHOLE_LINE (yuris only)
- Live after the fixes: r6 cold pass 90 lines (name entry answered on the hidden desktop), r7 fail 358 s: leak 1 (GDI hide confirmed on YU-RIS2), row 0.818, choice not measured; r9 (45 ms a character) inconclusive 426 s: cold pass 99 lines, leak 1, row 0.981, pair 1, the choice not measured (stalled on the hidden options again); r8 stalled on the prologue title card after the three name dialogs (clicks went out, the game did not move; r6/r7 went on 9 s later; not found)
- STILL OPEN, engine layer: the first choice (「（確かに、判断をするのは…）」 / 「（確かに、安易に…）」, r7 at line ~94) is drawn through the same TextOutA call as the dialogue, so the GDI hide on the selected YU-RIS2 stream blanks the option text too: the buttons are empty frames on the screen (r7 run/ocr-54.png), the cold run's OCR finds no options and the run stalls. The option texts reach the bridge on new YU-RIS threads at the moment of the draw (MeguLit_GDIHIDE hit at the same ms), so switching the hide off from the bridge comes too late for the first draw. # euphoria HD choice not translated, 2026-11-27 (#1143, PR #1295)
- Symptom: the first screen after 最初から始める is a choice (オープニングを見る / メインルームへ), shown in Japanese only. Cause: no dialogue stream yet; the bridge auto-selected YU-RIS2 (the TextOutA call, which also draws options, each glyph twice here) as the dialogue, the two options went out as one line 「AABB」, the choice detector dropped the pieces YU-RIS sent apart as "part of the line", OCR was never asked. The real dialogue stream is YU-RIS6 (0x41e3a4), which only speaks once the story starts
- Which stream is the dialogue is NOT the same for every YU-RIS game, so the skip is per build (version seed source.autoSelectSkip), not an engine default:
  - YU-RIS6 / EmbedYURIS6 carries the dialogue: euphoria HD (e77a1148, live), 女装山脈 (stream memory EmbedYURIS6 @41a9ac), サイコロジック・ラブコメ (stream memory EmbedYURIS6 @41b4ec)
  - YU-RIS2 carries the dialogue: Monochrome Empire (EmbedYURIS6 is inserted at 0x41d9ce but never opens a thread; the only dialogue is the 8x folded YU-RIS2 TextOutA stream, see above). A YU-RIS2 skip as engine default would leave it with no dialogue
  - How to tell for a new build: in hook-diagnostics.log look for `thread YU-RIS6` / `thread EmbedYURIS6` once dialogue is on screen (or the data/hook-streams/<exe>.json memory name). If it carries the lines, the build's version seed may set autoSelectSkip ["^YU-RIS2?$"] so a choice or system text drawn first is never taken as the dialogue; if only YU-RIS2 speaks, leave it unset
- Every engine (reader layer, core/choice-capture.cjs frameOf + hook-native auxText): a "line" made only of two or more distinct pieces other streams sent apart (each maybe drawn 2-3x in a row, no sentence end or quotes) is the options drawn together: the reader takes the line back and asks OCR for the options. So a build without the seed key still gets its first-screen choice translated
- Also fixed in the same PR (kernel / engine layer): the art scan's text is never a line while located options are on screen (it read the options, and a background misreading 「)第に」, as new lines that cleared the choice); a title menu read as separate one-row groups is a list; YU-RIS engine diff page.skipMergedTail 90 (Ctrl held: YU-RIS6 handed over 505 characters at once)
