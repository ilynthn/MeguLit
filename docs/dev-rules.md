# 开发细则：隐私、构建、测试、CI、第三方代码、禁止提交的文件

本文件由 AGENTS.md 拆出，条文原样保留，与 AGENTS.md 同样有约束力，冲突时以 AGENTS.md 为准，提交 PR 前须一并对照。提交与 PR 格式的完整条文见本文末尾。

## 用户数据、隐私与安全

- 用户数据位于安装目录下的 `data/`、`cache/`、`logs/` 和 `runtime/`，根目录可由 `MEGULIT_ROOT` 指定。测试和工具不得读写真实用户目录。
- MeguLit 不上传游戏内容。诊断和适配样本的上传须按 [docs/ADAPTER-PACKS.md](ADAPTER-PACKS.md) 的规则脱敏，并遵守用户的共享设置。
- API 密钥存于 DPAPI 保险库，不得写入设置文件、日志或诊断数据。签名密钥和 relay 令牌只能从环境变量或仓库外的文件读取，不得提交到仓库。
- 代码、测试、提交信息、PR 和 issue 中不得出现本机路径、用户名、邮箱、即时通讯账号、令牌等个人或敏感信息。

## 构建与测试

### 构建与本地运行

- 完整构建：`.\Build.ps1 -Check`，需要 Rust、Node.js 和 .NET 的 `csc`。环境问题可运行 `tools/check-env.ps1` 诊断。
- 本地应只运行与改动相关的测试：`.\Build.ps1 -TestsChanged`（按与 `origin/main` 的差异选择测试），或 `node --test validation/<文件>.test.cjs`。全量测试由 CI 执行。
- 修改原生代码时，须运行 `native/native-builds.json` 中对应组件的自测；修改 HookBridge 时须运行 `--self-test` 且退出码为 0；并运行 `node tools/native-stale.cjs` 确认二进制不早于源码。

### 缺陷修复与回归测试

每个缺陷修复都须附带回归测试，并满足以下要求：

1. **复现缺陷**：测试须重现 issue 或报告中描述的现象，使用与原始问题相同或等价的输入（剧本片段、钩子输出、设置组合等）。
2. **修复前失败**：须在修复前的代码（PR 的 base 提交）上运行该测试并确认失败，失败原因须与所修缺陷一致，不得因导入错误、夹具缺失等无关原因失败。
3. **修复后通过**：同一测试在 PR 的最终提交上通过。
4. **断言可见行为**：断言用户可见的结果（显示的文字、读音、译文落点、保存的数据等），不得只断言内部函数被调用。
5. **覆盖同类输入**：缺陷由某一类输入触发时，测试须覆盖该类输入的边界情况，并包含至少一个修复前已能正确处理的输入，证明修复没有破坏原有行为。
6. **记录在 PR 中**：PR 正文须写明新增或修改的测试文件、在 base 提交上的失败结果（失败的用例名或断言），以及在最终提交上的通过结果。

确实无法自动化测试的缺陷（例如必须启动真实游戏、依赖特定硬件或第三方服务），须在 PR 正文说明原因，并提供替代验证：复现步骤、修复前后的日志或截图，以及验证所用的游戏版本或环境。此类 PR 由维护者决定是否接受。

### 其他测试要求

- 测试应运行真实代码并断言用户可见的行为。只以正则匹配源码文本的测试无法证明行为，仅在无法运行真实代码时使用。
- 新增的条件分支和守卫，移除后须有测试失败。
- 修改默认值、字段或数据结构时，须同时运行改动文件相关的既有测试，不得只运行新增测试。
- 测试须使用自己的临时目录（`fs.mkdtempSync`，结束时清理），并以 `MEGULIT_WORK`、`MEGULIT_ROOT` 隔离，不得接触真实安装。
- 浏览器测试须使用独立的无头 Edge 配置目录，结束时关闭自行启动的进程。
- 测试不得在用户桌面上启动游戏、主程序或安装器。需要窗口的测试须经 `tools/run-isolated.cjs` 在隔离桌面中运行（`Build.ps1` 已默认如此）。
- 偶发失败须单独重跑并与 `main` 上的同一测试对比。在 PR 上稳定失败而在 `main` 上通过的，视为本次改动引入，不得以偶发为由放过。

## 持续集成

`.github/workflows/ci.yml` 包含 JavaScript 语法检查、原生组件构建（Windows）、`cargo check` 和三个测试分片。

- 仓库未设置必需检查。合并前须确认全部检查已完成且通过，不得使用自动合并。
- PR 的 CI 运行在与 `main` 合并后的代码上。处理失败时，先查看 TAP 输出中的 `not ok` 及用例名，再在同一 `main` 提交上复现，以区分本次改动与 `main` 上已有的失败。

## 第三方代码与许可证

- 新代码以 GPL-3.0-or-later 发布，源文件开头须带 `// SPDX-License-Identifier: GPL-3.0-or-later`。
- 参考或移植其他项目（剧本读取器、格式知识等）前须确认其许可证，并在 [THIRD-PARTY.md](../THIRD-PARTY.md) 按现有格式登记：项目、作者、链接、许可证、提交或版本、使用内容和落点文件。没有许可证的项目只能参考格式知识，不得复制代码。
- 引入的第三方代码须保留原许可证文件，并标明本地修改。

## 不得提交的文件

- 构建产物：`*.exe`、`*.dll`、`*.pdb`、`desktop/target/`、`runtime/`、模型文件。
- 用户数据与日志：`data/`、`cache/`、`logs/`、`*.sqlite`、`*.log`。
- `validation/` 下的测试输出。新增测试夹具须以 `git add -f` 添加，且不得包含游戏剧本全文或用户数据。
- 本机笔记，如 `HANDOFF-*.md`、`notes-*.md`。

## 提交与拉取请求（完整条文）


- 一个 PR 只解决一个问题，不夹带无关的清理。
- PR 标题和正文使用中文。正文包含「问题」「改动」「验证」三部分：问题描述用户可见的现象，改动说明修改位置和理由，验证列出实际运行的测试及结果。缺陷修复的验证部分须包含上文「缺陷修复与回归测试」要求的记录。
- 只陈述实际验证过的结论。未验证的内容须标注「未验证」或「推测」。界面外观的改动须附修改前后的截图。
- 关联 issue 须在正文中注明。只修复部分问题时写 `Refs #编号`，不得写 `Closes`。
- 允许在提交信息和 PR 中注明 AI 协助（如 `Co-Authored-By`）。无论是否使用 AI，提交者都须审阅最终改动，并对改动及其中的验证结论负责。
- 公开文字（PR 标题与正文、提交信息、issue、评论）中提及作品时，须写「游戏原名（中文名）」，例如「千恋＊万花（千恋万花）」，以便明确改动针对的游戏。原名使用正式发行的作品名；中文名取 VNDB 的中文标题或通行译名。可以附带成人内容。
- 多个工作区共用同一个 stash 列表，不得使用 `git stash`。改用临时提交或独立的 worktree。
